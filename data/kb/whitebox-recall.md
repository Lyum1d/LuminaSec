# 白盒召回：口径与实测（数字怎么读）

## 一、读召回前必须确认的三件事（顺序不能换）

⚠️ **这三个问题任何一个没答，数字就不能用。**

### 1. 分母是什么？

⚠️ DVWA 上的 100% 召回**不能信** —— 规则就是**照着那个形态调的**（拼接与 sink 同行）。换到真实项目会**大幅下降**。

⚠️ **先看分母口径**（v071）：检出常常是**部分的**（本机 669 个 `BenchmarkTest*.java` vs CSV **2740 条**标注），**73% 标注本机没源码** —— 算进分母会把召回**压成四分之一**。正确分母 =「**标注 ∩ 检出**」。
⚠️ **口径漂移的代价**：同一份代码，按旧口径（标注总数当分母）读出的是 **20.4%**，按正确口径读是 **82.1%**（v091）。**数字差 4 倍，代码一行没改。**

### 2. kind 级还是文件级？

⚠️ **（v072）** `crypto`/`hash` 共用 `weak_crypto`，文件级**100%** 里一半是**别类规则凑的**；按本类别规则只有 **51.4% / 73.7%**。**两个口径并排时读者会默认它们同口径 —— 比只显示一个更误导。**

### 3. 精确性的误报是谁报的？

⚠️ **精确性也会被口径骗**：`crypto` 一度显示 **51%**，拆开才发现那些"误报"**不是 crypto 规则报的**，是别类规则在同一文件里命中、被算到它头上；按 kind 归因后 **51% → 100%**。

⭐ **总教训**：**标尺本身也会错**。看到「召回很低」先别改规则，先查分母是不是把"本机没测到的用例"也算进去了。
⚠️ **别把 100% 读成"规则完美"**：它只说明**本机可命中的同类用例都被覆盖**，不代表精确 —— 且规则**不判数据流**：安全/漏洞变体常只差「参数是否可控」，要模型往上读才能定论。
**"别类规则的命中"不是"本类规则的误报"** —— 与「没测 ≠ 0 分」（v067）同族：**用一个不成立的归属去算指标。**

### 4. 你**自己写的探针**有没有真的在测东西？

⚠️⚠️ **（2026-10-06 实测）** 一个临时探针报「**cmdi 只有 22.9%**」，与项目 harness 的 **100%** 打架。
**查清后：探针错了，引擎没错。**

根因：规则对象上 `call_regex` / `regex` 是**惰性编译的方法**（`SinkRule.call_regex`），**不是字符串**。
探针写成 `re.search(r.call_regex, src)` —— 把 **bound method** 当 pattern 传进去，**每条规则都抛
`TypeError: first argument must be string or compiled pattern`**，又被 `except` 吞掉 → **全部记 0**。
正确写法是**调用它**：`pat = r.call_regex; re.search(pat() if callable(pat) else pat, src)`。

⭐ **量出来的是 22.9%（8/35），真值是 100%（35/35）—— 差的 27 处全是「调用者变量」形态**
（`Runtime r = Runtime.getRuntime();` + 下一行 `r.exec(...)`），**正是 `whitebox-miss-attribution` §一第 3 条 `@runner` 通道早就接上的那批**。
两通道实测**完全互补**：`call` 命中 8、`runner` 命中 27、**重叠 0、漏 0**。

**两条教训**：
1. **「我的探针」与「项目 harness」打架时，先怀疑探针** —— 本项目已发生**两次**
   （v060/v064「工具写错时，它造成的破坏会被误当成被测代码的问题」、本次）。
2. **静默的 `except` 会把「测不了」伪装成「测到了 0」** —— 探针**必须打印异常**，
   否则 0 分和「一条都没命中」长得一模一样。这与 v072「死代码通道让总数变好看」同族。

⚠️ **另外**：这 27/35 早在 `whitebox-miss-attribution` §一第 3 条就写明了，**我却当成新发现重新推了一遍** ——
**动手前先读 KB 的「漏在哪」一节**，可省一整轮。

## 二、⭐ 当前基线（v091 实测，项目自带 harness）

口径：分母 = 标注 ∩ 检出（可命中）；**kind 级**归因。

| 类别 | kind | 召回 | 备注 |
|---|---|---|---|
| cmdi | `rce` | 35/35 = **100%** | |
| crypto | `weak_crypto` | 19/37 = **51.4%** | 文件级 100%（别类规则凑的） |
| hash | `weak_crypto` | 28/38 = **73.7%** | 同上 |
| pathtraver | `path_traversal` | 38/38 = **100%** | |
| sqli | `sqli` | 54/64 = **84.4%** | 仍是最大缺口（v090 46.9% → v091 84.4%） |
| **小计** | | **174/212 = 82.1%** | 精确性 67.7% |

⭐ **两版的账分开记**：**v090 的 +7 例**来自 taint 层两处修复（`whitebox-miss-attribution` §一第 6、7 条），**误报零新增**；
**v091 的 +17 例**来自调用名扩充（见 `whitebox-sink-triage` §一），代价 **+5 例安全用例命中**
（精确性仍从 58.8% 升到 66.7%）。合起来 sqli **46.9% → 84.4%**，其余四类召回 **Δ=0**。
⚠️ **剩余 10 例的构成要按实测读**（v091 逐例查过、**v093 逐条实现并量过**，**都不是推断**）：
**6 例 `switch` 分支** + **1 例 helper 间接取值** + **3 例检索层边界**（嵌套 lambda 参数区 ×2、无参 `executeBatch` ×1）
—— 后 3 例 v093 **实测否决**：嵌套 lambda 那 2 例要靠**裸 `query`/`update`** 才能捞回，
而裸 `update` 在 Benchmark 上新增的 47 条命中里绝大多数是 `md.update(input)`（`MessageDigest`，与 SQL 无关）；
`addBatch` 那 1 例要拿 **+2 例新误报**换（精确性反降）。证据与判据见 `whitebox-miss-attribution` §三。
⇒ **不要把 84.4% 当成"不做常量折叠时的上限"**（v091 之前的说法，实测不成立）；
但也**不要以为这 3 例"还没修"就是欠账** —— 它们是量过之后**主动不修**。

⚠️ **文件级召回是 203/212 = 95.8%** —— 比 kind 级多出的 **29 个是"别类规则在同一文件里命中的"**，不是本类别规则的功劳。**这就是为什么主值要用 kind 级**（见 §一）。
（本表由项目自带 harness 跑出：`app.codebase.batch.run_batch`，配置 `data/recall_batch.json`。）

**能力外（无对应规则，低召回属预期、单列不计小计）**：`xss` 0/65、`weakrand` 31/65、`trustbound` 2/17、`xpathi` 3/3、`ldapi` 0/4、`securecookie` 1/10。

⚠️ **余量最大的仍是 sqli。**

## 三、一页速查

| 你在看什么 | 必须同时问 | 去哪 |
|---|---|---|
| 一个召回数字 | 分母是不是「标注 ∩ 检出」？ | 本文 §一 |
| 一个精确性数字 | 误报是本类规则报的吗？ | 本文 §一 |
