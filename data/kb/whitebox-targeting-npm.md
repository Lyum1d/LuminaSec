> 白盒**打哪个目标**（选靶篇 · **npm/JS 生态**）。姊妹篇：`whitebox-targeting`（**Java/Maven 选靶**）、
> `whitebox-toolchain-npm`（**npm 工具链与判据**：pattern-first、新代码 diff、交付坑、不烧清单）、
> `whitebox-guard-review`（**守卫写对没有/我的脚本对不对**）、`whitebox-audit-method`（**拿到代码之后怎么审**）、
> `whitebox-sink-triage`（**命中怎么分类**）、`whitebox-recall`（**召回数字怎么读**）、
> `whitebox-miss-attribution`（**漏报怎么归因**）、`whitebox-disclosure-gate`（**找到之后能不能报**）。
>
> 本篇来自 **2026-09 至 10 的 23 轮 npm 实测**。**结论是"半个负面结果"**：
> **在 npm 下载量头部按"类别/模式"找洞，产出率会趋零 —— 这是分布决定的。**
> 它的价值在于**把"什么时候不该打"写成可判据的东西**。
> 工具怎么用、坑在哪 → `whitebox-toolchain-npm`。

# 白盒选靶与产出策略（npm / JS 篇）

## 〇、与 Java 篇的差别（先看这条，别照搬）

| 维度 | Java/Maven 篇（`whitebox-targeting`） | **npm/JS 篇（本篇）** |
|---|---|---|
| 源码获取 | 拉 `sources.jar` | `registry.npmjs.org/<pkg>` 取 `dist.tarball` → 解包 |
| 公开记录 | OSV（`ecosystem=Maven`）+ GitHub | OSV（`ecosystem=npm`）+ GitHub issues/PR |
| **"真实用户"代理** | 下载量难拿 | ⭐ **`api.npmjs.org/downloads/point/last-month/<pkg>` 直接给月下载量** |
| 高频陷阱 | 守卫在**底层依赖**里 | **打包产物**（单 chunk 把 node_modules 全打进去）／**纯原语 vs 校验器** |
| 发版节奏 | 慢 | **极快**（同一天可有几十个头部包发新版） |

⭐ **npm 的下载量 API 是本篇最重要的工具** —— 它让"闸 4（真实用户）"第一次有了**可量化的代理**。

---

## 一、⭐⭐ 核心结论：**结构性张力**（23 轮实测，务必先读）

把第 17~23 轮连起来看：**连续 7 轮、约 20 个假设、0 条可上报**，且每次失败原因都指向同一件事：

```
        未被审计  ⟺  下载量小  ⟺  闸 4 不通过（不可上报）
        下载量大  ⟺  已被审计  ⟺  找不到东西
```

**这是一个根本性张力，不是方法问题。** 推论：

> **在「npm 下载量头部 + 找老代码」这条路上，产出率会趋零。**
> 因为"值得报"要求**同时**满足"没被审计过"与"有真实用户"，而这两个条件在下载量分布里**近乎互斥**。

### 一轮轮试过的"破法"，以及为什么都没成

| 尝试 | 轮次 | 结果 |
|---|---|---|
| 换判据：从"自称安全"→"状态一致性" | 15 → 16 | ⭐ **16 轮命中 1 条**（此后同法不再出） |
| 换子类：锁租约 / 限流窗 / 重试退避 | 17 | 0（4 个强候选**全被公开记录挡下**） |
| 换方向：失败即放行 | 18 | 0（3 个假设全证伪） |
| 换方向：攻击者可控 | 19 | 0（4 个假设全证伪；**同族 CVE 已全修**） |
| 换判据：隐含不变量（不变量词筛） | 20 | 0（2 个候选逐行验证正确） |
| **换轴：按代码模式选靶** | 21 | 0（模式真阳性 **0/60**） |
| **换轴：审计新版本 diff** | 22/23 | 0（**新代码几乎全是"加固向"**） |

⭐⭐ **关键观察（22/23 轮）**：读到的**每一个新版本改动方向都是"加固"** ——
`cookies` 把宽松正则换成严格 RFC 6265、`compression` 修资源泄漏、`jose` 新增 RSA≥2048 校验、
`oracledb` 新代码是校验密集型。
⇒ **npm 头部生态的发布流本身在持续加固**，"找最新代码"这条破法也因此失效。

### 那什么时候该收手

**当连续 ≥3 轮 0 产出，且每一轮的原因是"公开记录挡下"或"已验证正确"时** ⇒
不要再换轴，**换线**（转 SRC 实战线 / 换成自己的项目），或**把方法论本身作为交付物**。

## 二、⭐ 判据修正：**不要找"宣称自己安全"的组件**

第 19 轮最重要的产出。因为**宣称会吸引审计** ⇒ 宣称安全的组件是**最卷、被审得最彻底的赛道**。

| 判据 | 靶子特征 | 23 轮命中记录 |
|---|---|---|
| ❌ **宣称的安全属性** | 卖点就是"安全 / 防护 / 校验" | **0 命中**（第 15、17、18、19 轮全落空） |
| ✅ **隐含的不变量** | 作者**没把"安全"当卖点**，但代码里有一条必须成立的假设 | ⭐ **命中**（第 13、16 轮） |

**两个命中实例（用来校准感觉）**：

| 轮 | 靶子 | 卖点 | 隐含的是什么 |
|---|---|---|---|
| 13 | `safe-expr-eval` | "whitelisted operations" | 不变量的**实现**隐含在 registry 语义里（`in` vs `Object.hasOwn`） |
| 16 | `express-idempotency-middleware` | "idempotent" | **从没提过"冲突检测的完整性"** ⇒ 前缀截断导致同 key 不同 payload 被当重放 |

⭐ **可操作问法**：**「这个包的正确性依赖哪条它自己没写出来的假设？」**
候选方向：并发的**顺序假设** / 序列化的**往返假设** / 货币单位的**精度假设** /
标识的**唯一性假设** / 时间戳的**单调性假设**。

### 筛选词也要跟着换

- ❌ 别用安全词捞池（`secure` / `prevent` / `protect` / `guard` / `sanitiz` / `escap`）
  ⇒ 捞出来的正是那个最卷的赛道；
- ✅ 用**不变量词**：`unique` / `monotonic` / `exact` / `precise` / `lossless` / `faithful` /
  `deterministic` / `sortable` / `ordered` / `atomic` / `consistent` / `guarantee` / `collision`。

**实测筛选效率**（npm search 描述命中率）：

| 轮 | 筛选词 | 命中率 |
|---|---|---|
| 16 | 安全词 | 106/257 = 41% |
| 18 | 安全词 | 42/165 = 25% |
| 19 | 安全词 | 52/160 = 33% |
| **20** | **不变量词** | **68/170 = 40%** |

⇒ **筛网宽度相当，但指向的赛道不同** —— 这才是换词的意义。

## 三、⭐⭐ 四问筛子（按序自检，每条都有实测依据）

> **① 下载量够吗？ ② 失败方向是「多放行」吗？ ③ 防护对象是「攻击者」吗？ ④ 公开记录干净吗？**

### ① 下载量够吗（闸 4 的量化代理）

`api.npmjs.org/downloads/point/last-month/<pkg>`。**比 star 可靠得多。**
经验线：**≥10 万/月**才考虑；**≥100 万/月**才是"真实用户"级别的靶子（也意味着更可能已被审透）。

⚠️ **包名里的反例**：`nanohttpd` 在 OSV 是 0，CVE 却挂在兄弟包 `nanohttpd-nanolets` 上
（Java 篇同款教训）⇒ **OSV 反查要覆盖同族/同 scope 的全部包**。

### ② 失败方向是「多放行」吗（第 17 轮沉淀）

| 失败方向 | 例子 | 是否安全问题 |
|---|---|---|
| **多放行**（绕过 / 双持有 / 重复执行 / 返回陈旧许可） | 限流被绕、锁被双持、幂等键重复执行 | ✅ 通常是 |
| **少放行**（卡死 / 抛错 / 拒绝一切） | 某调度库调一次 `updateSettings()` 后**永久停掉内部刷新** | ❌ **不是**（是自身可用性） |

⭐ **第 17 轮实测反例**：某调度库（5,400 万/月，休眠 3.5 年、OSV=0、本地可测、**判据全部对**）
—— 但它 **fails-CLOSED**，且触发点是**应用自己调用** ⇒ **无攻击者可控路径** ⇒ 按纪律**不写安全报告**。
**"有真 bug" ≠ "是安全问题"。**

### ③ 防护对象是「攻击者」吗（第 18 轮沉淀）

- ✅ **防护对象是攻击者/恶意输入**：限流、鉴权、校验、沙箱、防重放、签名校验；
- ❌ **防护对象是"故障"**：某熔断/重试/降级库这类**弹性库**
  ⇒ 即使 fail-open 也**不构成安全问题** ⇒ **不烧**。

### ④ 公开记录干净吗

**活跃维护的包：先去翻 issue/PR（含 closed）** —— 第 17 轮四个强候选
（`limiter` / `@fastify/rate-limit` / `@upstash/ratelimit` / `redlock`）
**全部**因为已有 open issue/PR 覆盖同类问题而被排除。
⭐ **休眠包反而更值得看**（第 17 轮那个调度库就是这么浮出来的）。

## 四、一页速查

| 步骤 | 动作 | 判据 / 坑 |
|---|---|---|
| 1 | **定必要条件** | 一句话说清"有该问题的必要条件"；优先**隐含不变量**（§二） |
| 2 | **量化下载量** | `api.npmjs.org/.../last-month/<pkg>`；≥10 万才考虑，≥100 万才算真实用户 |
| 3 | **OSV 反查** | `ecosystem=npm`；**覆盖同族/同 scope 全部包**；正着用 = 挑已修过的 |
| **3.5** | ⭐ **前置公开记录检查** | **OSV + GitHub issues + PR（含 closed）**；活跃包必翻 |
| 4 | **四问筛子** | 下载量 / **失败方向（多放行？）** / **防护对象（是攻击者？）** / 公开记录 |
| 5 | 出候选 | **查它在哪个版本被修**；判"是不是一直如此" |
| 6 | **PoC 是分水岭** | 别停在"结构上存在"；且要设计多个向量 |
| 7 | 交付 | ⚠️ **查退信**；⚠️ **别附 `.js`/`.mjs`** → 工具链篇 §二 |

## 五、收尾：这段实测最诚实的结论

1. **方法是对的，但靶场选错了** —— 23 轮里只有 2 轮（13、16）命中，且都落在"隐含不变量"上；
2. **头部生态的加固速度超过审计速度**（22/23 轮实证）⇒ 拿"高下载量"当门槛，等于拿"已被审过"当门槛；
3. ⭐ **这条线的最大价值不在产出，而在"把什么时候不该打"变成了可判据的东西** ——
   本篇 §一 / §二 / §三 / §四 就是那套判据。
4. ⭐ **唯一那条有效命中（第 16 轮）完整跑通了**：选靶 → 四道闸 → 上报 →
   **送达 → 维护者回信"我会修"**。**这证明方法论本身有效**，问题只在"靶场存量"。
