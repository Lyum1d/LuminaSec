> 白盒**找到之后能不能报出去**（披露篇）。姊妹篇：`whitebox-targeting`（**打哪个目标**）、`whitebox-guard-review`（**守卫写对没有/我的脚本对不对**）、`whitebox-audit-method`（**拿到代码之后怎么审**）、`whitebox-sink-triage`（**命中怎么分类**）、`whitebox-recall`（**召回数字怎么读**）、`whitebox-miss-attribution`（**漏报怎么归因**）。
> ⭐ npm/JS 生态另见 `whitebox-targeting-npm`（选靶）、`whitebox-toolchain-npm`（工具链）。
> 一句话：**「洞真」与「能报」是两件事** —— 中间隔着四道**互相独立**的闸，**别用一道的结论去顶另一道**。
> ⚠️ **本篇只管「这个能不能报」**；「打哪个」「怎么审」「怎么分类」见上面五篇。

# 披露判定：四道闸

## 〇、为什么单开一篇

第八~十一轮实测，**四次「看着像 0day」全部停在披露前**，而且**每一次拦住它的都不是同一道闸**：

| 轮 | 靶子 | 洞真吗 | PoC | 拦住的是哪道闸 |
|---|---|---|---|---|
| 8 | `stream-unzip` | 解压条目名**原样透出**（5/5 恶意名逐字返回） | ✅ | **闸 1**：README 明说 "treat as untrusted input" |
| 9 | `node-unzip-2` | 自身**零清洗**（`entry.path = fileName` 直传） | ✅ 端到端 3/3 **未逃逸** | **闸 2**：守卫在底层 `fstream` 的 `path.join('/', pp)` |
| 10 | `ssrfcheck` | `hostIsIp &&` 罩住全部私有段检查 → 域名形式 **8/9 放行**（对照组 IP 字面量 5/5 全拦） | ✅ | **闸 3**：issue #4(2024)/#7(2025) **早已公开** |
| 11 | `ssrf-req-filter` | 1.1.1 里 3 个缺陷俱在（同步 throw **进程级崩溃**、无 host 放行、每 URL 新建 Agent） | ✅ | **闸 4**：PR #56 已合 master，但**版本号未 bump、npm 未发** |

⭐ **四次都不是"眼力不够"，是"少过了一道闸"。** 四道闸必须**逐道过**，且**顺序固定**。

---

## 一、四道闸（任一道不过 ⇒ 不报）

| # | 闸门 | 一句话判据 | 不过的反例 |
|---|---|---|---|
| **1** | **「没守卫」≠「有洞」** | 这个"没做"是不是**已被文档声明的接口契约**？ | `stream-unzip` README：*"these should be treated as untrusted input"* |
| **2** | **「守卫」可能不在你读的那个库里** | 把数据流**跟到最底层依赖** —— 谁最终决定它落到哪 | `node-unzip-2` → `fstream/lib/dir-writer.js` 的 `path.join(self.path, path.join('/', pp))` |
| **3** | **「有洞」≠「能报」** | **公开记录是独立的闸**，且**必须查到 issue/PR 层**（不能只看 OSV） | `ssrfcheck` OSV 仅 2 条，**我这条不在其中**；issue #4/#7 才是决定性的 |
| **4** | **「已修」≠「已修到用户手上」** | 修在 master，但**版本号 bump 了吗？发布了吗？** | `ssrf-req-filter`：PR #56 已合，npm latest 仍是 1.1.1（2024-05-11） |

⚠️ **四道闸对应四种完全不同的"不报"理由，不能互相代替**：
- 闸 1 不过 = **根本不是缺陷**（是契约）；
- 闸 2 不过 = **不是这个库的缺陷**（是选错了层）；
- 闸 3 不过 = **是缺陷，但不是新发现**（别人已报）；
- 闸 4 不过 = **是缺陷且已修，只差发版**（是流程问题，不是研究发现）。

---

## 二、逐道展开

### 闸 1 · 「没守卫」≠「有洞」—— 先读文档，判「契约」还是「疏漏」

同一个"没做清洗"，**性质由文档决定**。三种形态：

| 形态 | 例子 | 判定 |
|---|---|---|
| ① **声称安全却没做** | 库里自称 `isSafe()`／README 承诺 sanitize，实现里没有 | ✅ **是洞** |
| ② **明说**是调用方责任 | README："treat as untrusted input"、"not a security boundary" | ❌ **不是洞** |
| ③ **什么都不说** | 既没承诺也没免责 | ⚠️ **灰色**（design smell，不足以报） |

⭐ **判 ② 的现成样板**：`request-filtering-agent` PR #39（2026-09-29）标题就是
`docs: describe that denyIPAddressList is not a security boundary` ——
**维护者主动把"这不是安全边界"写进了 README**。这类库的"绕过"类发现**一律不报**。

⚠️ **「没测试」最容易被误用**：读起来像"作者没意识到"，但文档说"意识到了"。
**两边都要读** —— 只读代码会把它判成疏漏，只读 README 会漏掉实现与自称不符的情况。

### 闸 2 · 「守卫」可能不在你读的那个库里 —— 跟到**最底层依赖**

审"库 A 安不安全"**不能只看 A**：A"没清洗"可能只是把清洗**委托**给了 B。
**别只问"谁接收了不可信输入"，要问"谁最终决定它落到哪里"。**

实测（第九轮）：`node-unzip-2` 的 `lib/parse.js` 里 `entry.path = fileName` **原样**，
`lib/extract.js` 直接喂给 `fstream` 的 `Writer({ type:'Directory', path: opts.path })` ——
**看着毫无防护**。但 `fstream@1.0.12` 的 `lib/dir-writer.js:128-129` 有：

```javascript
// get rid of any ../../ shenanigans
props.path = path.join(self.path, path.join('/', pp))
```

⇒ 用**真实运行时**端到端验证：3 个 `../` 名**全部被中和**、零逃逸、canary 完好。

⚠️ **同族陷阱 ①：拿"错误语义的脚本"去"证明"漏洞。**
第九轮我用 `posixpath.join(base, '/x')` 模拟 Node 的 `path.join` —— 前者**遇绝对路径会丢弃 base**，
于是模拟器把"安全"算成了"有洞"，**差点写出一份假报告**。
**`path.join` 的语义必须用真实运行时（Node）复核，不能用 Python 的 `join` 类比。**

⚠️ **同族陷阱 ②：只审第一层库。**（中间库外包给下游时，只看中间层必然错）

⚠️ **同族陷阱 ③：把"依赖有公告"当成"这个包有洞"。**
`fstream` 只有 tar-hardlink 的 CVE-2019-13173，**与 zip-slip 无关**。

### 闸 3 · 「有洞」≠「能报」—— 公开记录是**独立**的一道闸

⭐⭐ **这是最容易漏、代价最大的一道。** 洞真、PoC 跑通、根因清楚、还有对照组 ——
**仍然可能不可报**，因为"是否已被人报过"与"洞真不真"**完全无关**，只能靠**查**。

查什么（**三路都要**）：

| 源 | 查什么 | 陷阱 |
|---|---|---|
| **OSV**（`api.osv.dev/v1/query`） | 有无 CVE/GHSA | ⚠️ **"OSV 干净" ≠ "没人报过"** |
| **GitHub issues**（`is:issue`） | 含 **closed** —— 已关闭的往往就是"已被处理" | ⚠️ 必须翻到底，别只看第一页 |
| **GitHub PR**（`is:pr`） | 含 **closed** —— **"公开未合"** 是典型盲区 | ⚠️ 要打开 PR 正文看它修了什么 |

⚠️⚠️ **必须查到 issue/PR 层，不能只看 OSV**。实测两次：
- `ssrfcheck` 在 OSV 上**只有 2 条**（CVE-2026-43929 / CVE-2025-8267），
  **我实测的那条不在其中** —— 只看 OSV 会误判成"新发现"；
  真相是 **issue #4（2024-04-08，closed，"Possible bypass using DNS rebinding"）**
  与 **issue #7（2025-10-15，open）**（链 SocketDev 公告 `GHSA-2w7q-qwcg-x5mg`，Pending CVE）。
- `ssrf-req-filter` 在 OSV 上 **0 条** —— 看 OSV 会以为它是"从未有安全问题的干净包"，
  而它有三个**已公开讨论并已修**的缺陷（issue #38/#41/#49 + PR #56）。

⭐ **同族已三次**：`jarchivelib`（PR #66 自 2018-06-28 公开未合）、`ssrfcheck`、`ssrf-req-filter`。
⇒ **不是偶发，是选靶阶段的系统性盲区。**

⚠️⚠️ **文档里"互相矛盾"的表述也不足以支撑披露。**
`ssrfcheck` README 同时写着 "cannot be a private IP of **any** range"（像在声称全覆盖）
与 "does not garantee the **DNS layer** sucurity"（又免责了 DNS 层）——
**看起来像"声明与实现不符"（闸①形态）**，但 issue #4/#7 证明**维护者早已知道并公开讨论过**。
⇒ **公开记录才是决定性的；文档矛盾只是提示，不是证据。**

### 闸 3b · ⭐⭐ 记录的**第三种结局**：三路都干净 ⇒ 结论是「**已尽力、未找到**」，不是「值得报」

前两种结局是"被挡下"（闸 3）与"通过"（可报）。**还有一种最容易被自己骗的**：
OSV/GitHub/PR **三路全干净**，而且**我确实找不到洞** ——
此时**不要**为了"这轮总得有产出"而把一个边缘现象包装成漏洞。

第十四轮实测（`resolve-path@1.4.0`，pillarjs，Express 生态）：

| 检查 | 结果 |
|---|---|
| 闸 1 契约 | ✅ **形态①成立** —— README 明确列 "malicious" 清单（绝对路径 / NULL / **解析到 root 之外** / 越过再回来），**无免责**；示例正是静态文件服务标准用法 |
| 闸 2 层级 | ✅ 守卫自持（`pathIsAbsolute.posix() \|\| .win32()` + 带段边界正则 `/(?:^|[\\/])\.\.(?:[\\/]\|$)/`） |
| 闸 3 公开 | ✅ **无既有记录** —— issues **closed=0**（open 仅 1 条讲 depd，无关）；**PR 39 条全是 dependabot bump / CI，无一条触及安全逻辑**；OSV 仅 CVE-2018-3732（1.4.0 已修） |
| 实测 | **959 例**字符串穷举 + **28 例**非字符串/鸭子类型 + 原型污染 ⇒ **0 逃逸**，非字符串 **28/28 抛错**（fail-closed） |

⇒ **正确产出是「0 可报」，并且要写明"我搜了什么、没搜什么"**：
一个**自称 with validation、8 年零发布、被广泛使用**的包，在**我能构造的输入空间里全部守住**。
**这是有效的负面结果，不是失败。**

⚠️⚠️ **两条纪律**：
1. **「三路都干净」≠「一定藏着一个洞」** —— 它也可能就是**写对了**。
2. **「干净」与「没查」必须分开记**（否则下一轮会重查一遍）：
   - ❌ "没查到"（查了、干净）
   - ❌ "没得查"（包没有安全断言 ⇒ 必要条件不成立，见 `whitebox-targeting` §一③b）
   - ✅ **两者都要写进记忆，且要标明是哪一种。**

⭐ **代价不对称仍在**：把"没有洞"强行说成"有洞"，比"如实报 0"坏得多 ——
**会削弱已发出的真报告的可信度。**

### 闸 4 · 「已修」≠「已修到用户手上」—— 但要分清这是**流程问题**

⚠️ **同一个事实，两种读法**：

| 读法 | 结论 |
|---|---|
| "master 修了、npm 没发 ⇒ **仍在影响所有用户的未修复漏洞**！" | ❌ **错**（这是把流程问题当研究发现） |
| "master 修了、npm 没发 ⇒ **维护流程滞后**" | ✅ **对**（公开记录完整 ⇒ 不是新发现） |

实测（第十一轮，`ssrf-req-filter`）—— 硬证据链：

```
① PR #56 [harden SSRF filter]   merged = true   2026-08-04
② master lib/index.js           ✅ 已含 isNonHostConnection / destroyBlocked / 单例 agent
③ master package.json version   = 1.1.1          ← ⚠️ 没 bump
④ npm dist-tags.latest          = 1.1.1          发布于 2024-05-11
⑤ npm tarball 1.1.1 实际代码    ❌ 第 31 行仍是 throw new Error(...)，无 isNonHostConnection
```

⭐ **第 ⑤ 步才是决定性的** —— **必须下 tarball 解包逐字比对**，
**不能从 tag / 版本号推断**（`registry.npmjs.org/<pkg>/-/<pkg>-<ver>.tgz`）。

⚠️ **为什么"已合未发"不可报**：缺陷**已公开**（issue #38/#41/#49 + PR #56，2023~2026）、
**维护者已知已修**、**只差发版** ⇒ 属**维护流程问题**。
把它当 0day 报 = **把别人的工作重新包装**（`jarchivelib` 同族，**第三次**）。

⚠️ **别混淆两种"已公开"**：
- 「**公开未合**」（`jarchivelib` PR #66）—— 有人报了、维护者没合、**缺陷仍在**，但**已公开**；
- 「**已合未发**」（`ssrf-req-filter` PR #56）—— 维护者修了、没发版。

⭐ **两者的共同点：公开记录完整 ⇒ 都不是安全研究的新发现。**
差别只在"要不要提醒维护者发版" —— 那属于**沟通**，不属于**披露**。

---

## 三、⭐⭐ 顺序：公开记录检查要**前移**到选靶阶段

⚠️ **第十轮就是顺序反了**：先审代码 → 写了一套 PoC → **最后才查公开记录** → 发现早已被报过。
**一整套 PoC 白写。**

⇒ **公开记录检查应作为选靶流水线的「第 2.5 步」**，插在「OSV 反查」之后、「代码自检」之前：

```
必要条件定候选 → OSV 反查 → ⭐ 前置公开记录检查 → GitHub 复核 → 代码自检守卫
                            （OSV + issues + PR，含 closed）
```

⚠️ **别把"前置"理解成"少查一次"** —— 前置只是**顺序**变了，**查的东西一样多**：
写 PoC 之前先查一遍（挡掉已公开的），**PoC 跑通之后再终检一遍**（挡住"跑通了才发现已公开"）。

⭐ **前置的实测收益（第十一轮）**：8 个候选一次过完，**5 个在选靶阶段即被排除**，
包括两个"若不前置就会白写 PoC"的：
- `request-filtering-agent` → 闸 1（PR #39 标题直接写着 "not a security boundary"）；
- `superstruct` → 闸 3（#1301 是 0sec 已提的 TOCTOU 绕过）。

**净收益 = 省两套 PoC。**

## 四、一页速查

| 顺序 | 闸 | 问自己 | 不过就…… |
|---|---|---|---|
| 1 | 契约 | **文档说这是谁的责任？** | 不是缺陷，停 |
| 2 | 层级 | **守卫是不是在底层依赖里？**（跟到底） | 不是这个库的洞，停 |
| 3 | 公开 | **OSV + issues + PR（含 closed）都查了吗？** | 不是新发现，停 |
| 4 | 落地 | **修了之后，发版了吗？**（下 tarball 比对） | 是流程问题，不报 |

⚠️ **四道闸全过，才轮到写报告**。**任一道不过都不报** ——
把灰报成黑，**损害报告人信誉，并连带削弱已经发出去的第一条真报告**（代价不对称）。

⭐ **写作纪律**：报告里**只写过了四道闸的那一条**；
**被否掉的候选照实写进研究记录**（"被测算否掉的方案也是产出"），但**不进报告**。

> 相关：`whitebox-targeting` 的四步流水线、`whitebox-audit-method` 的四问闸门、
> `whitebox-sink-triage` 的候选分类、`whitebox-recall` 的口径、`whitebox-miss-attribution` 的归因。
