> 白盒**打哪个目标**（选靶篇 · **Java/Maven 生态**）。
> ⭐ **靶子在 npm/JS 生态请另读 `whitebox-targeting-npm.md`**（23 轮 npm 实测：**「结构性张力」**、
> **判据修正**（别找"宣称安全"的）、**四问筛子**）。
> ⭐ **npm 工具链与判据另读 `whitebox-toolchain-npm`**（pattern-first 两段式 / 新代码 diff 流水线 / 交付坑 / 高频假阳性 / 不烧清单）。
> 姊妹篇：`whitebox-guard-review`（守卫写对没有/我的脚本对不对）、`whitebox-audit-method`（怎么审）、`whitebox-sink-triage`（命中怎么分类）、`whitebox-recall`（召回数字怎么读）、`whitebox-miss-attribution`（漏报怎么归因）、`whitebox-disclosure-gate`（**找到之后能不能报**）。
> 本篇回答的是「**值不值得打**」—— 它决定产出的**数量级**，与工具能力同等重要（六轮实测，见 §〇）。

# 白盒选靶与产出策略

## 〇、先接受一个事实：**产出上限由选靶决定**

六轮实测（2026-10-05 / 10-06）：

| 轮次 | 靶子 | 判据 | 结果 |
|---|---|---|---|
| 1 | zt-zip 1.12 | 从 CVE 库**正着**挑 | 1 个候选（性质是**已知 CVE 的修复不完整**） |
| 2 | rdf4j / ESAPI / Openfire | 同上（路径穿越） | **0** |
| 3 | Apache Santuario | **换类别**（XXE） | **0** |
| 4 | **jarchivelib** | ⭐ **OSV 反查**（靶子无该类 CVE 历史） | ⭐ **第一击就中**（**真 PoC 跑通**） |
| 5 | rome / poi / xom / saxon | 同上（XXE） | 0（全都已硬化） |
| 6 | nanohttpd 等 | 同上（路径穿越） | 0（有显式守卫） |
| 7 | **jlhttp 3.2** | 同上（路径穿越 + 必要条件筛选） | ⭐ **命中**：`serveFile` 的前缀校验**没补分隔符** → 兄弟目录逃逸（**原始 socket PoC 跑通，5 个向量**；1.3~3.2 **全版本未修**；OSV 扫整个 `net.freeutils`=0 条、GitHub 0 条） |

⭐ **前三轮 5 个项目 0 命中；第四轮只换选靶方式，第一击就中。**
**同一个工具、同一个模式，产出从 0 变成 1** —— **选靶策略和工具能力一样决定产出。**
⭐ 第七轮（jlhttp）**复现了第四轮的成功**：四步流水线走完，第一击命中。
**流水线可重复，不是运气。** 同一轮里另外三个候选**全部排除**（理由见下 §二·五）。

⚠️ 第二节那条「换类别」的推论**曾经写错并指导过一轮**（第二轮提的，第三轮被实测推翻）。
**被实测推翻的建议必须回写文档** —— 否则后面每一轮都会白跑。

## 一、⭐⭐ 期望管理：三类「没戏的靶子」

**有 CVE 记录的项目，最新版往往已把守卫补齐。** 所以「读 CVE 补丁 → 全库找同模式漏点」这条路，
真实产出是**「已知 CVE 的修复不完整」**与**方法可行性验证**，而**不是稳定产出存活 0day**。

由此推出三条**反直觉**的判据：

**① 过滤条件不是「漏洞类别」，而是「该项目有没有该类 CVE 的历史」**
有过 = 该类**已被强制审过一遍**。
- 实测：路径穿越（rdf4j / ESAPI / Openfire）**0**；
- **换类别**查 XXE（Apache Santuario）**仍然 0** —— **换类别救不了**。
→ ⭐ **从 CVE 素材库里挑靶子 = 专挑已经修过的地方**（自相矛盾）。

**② 「无 CVE」≠「无人知道」** —— OSV 查完**还要查 GitHub issues/PRs**：
- 两边都干净 → 可能真没被审过（值得投入）；
- **有公开讨论但无 CVE → 「已知未修的流程盲区」**
  （SCA 工具对它**零告警**，仍有价值，但 **别叫 0day**）。
- 实测：`jarchivelib` 在 OSV 里 0 条，却躺着 **2018-06-28 提交、至今未合并的修复 PR**。

**③ 「0 CVE」还分两种** —— 再补一步**查代码本身**（守卫在不在、集中在哪）：

| 形态 | 含义 | 处置 |
|---|---|---|
| **守卫一处都没有** | 真没审过 | ✅ **值得深挖**（jarchivelib） |
| 主路径**带守卫 + 注释引旧公告** | 早年审过 | ❌ 排除（ROME 引 **2002 年** SecurityFocus 公告） |
| **守卫集中在单一入口** | 结构性安全 | ❌ 排除（POI 五类工厂全硬化在**一个文件**里） |

⭐ **守卫的「位置」也是信号**：集中在一个文件 = 结构性安全；散落/缺失 = 有戏。

⭐ **「0 CVE」共四种含义、「守卫写对没有」、以及「我自己脚本判据写错」→ `whitebox-guard-review`。**
（另一种最阴的：**包没有安全断言 ⇒ 没有可审的东西**，`mkdirp`/`tempy` 属此类。）

⭐⭐ **但"有守卫"还要看守卫**写对没有** —— ⚠️「做了规范化」≠「校验写对」（v094 实测，jlhttp）**

同一个坑有三种写法，**只有前两种是对的**：

| 写法 | 判定 |
|---|---|
| `file.toPath().startsWith(base.toPath())` | ✅ 按**路径元素**比较（正确） |
| `file.getPath().startsWith(base.getPath() + File.separator)` | ✅ 补了分隔符（正确） |
| `file.getPath().startsWith(base.getPath())` | ❌ **字符串前缀**比较 → `…\www-secret` 会被 `…\www` 匹配 → **兄弟目录逃逸** |

⚠️ jlhttp 的 `serveFile` 就是第三种，而且它**做了** `getCanonicalFile()` ——
所以这**不是**"忘了规范化"，是**校验本身写成了字符串前缀**。
**光看"有没有 getCanonicalPath"会把它判成已加固** —— 这正是本节开头那条告诫的又一个实例。
实测：原始 socket `GET /../www-secret/secret.txt` → **200 读到兄弟目录文件**（5 个向量全通）。

⚠️ **判「有守卫」不能只看关键词，要看布尔值**（实测踩到）：
`SUPPORT_DTD` / `IS_SUPPORTING_EXTERNAL_ENTITIES` **设成 `true` 是开启 DTD** 而非关闭。
第一版扫描器写成「关键词出现即算有守卫」，差点把 `SUPPORT_DTD=true` 判成已加固。

⚠️ **「不确定」要如实标出，别当「干净」**：有的库解析代码不在该 artifact 的 sources jar 里
（实测 `poi-ooxml` / `jaxb-runtime`）—— **没证据 ≠ 没问题**。

## 二、⭐ 选靶流水线（四步 + 一道前置闸，实测有效）

```
必要条件定候选  →  OSV 反查  →  ⭐前置公开记录检查  →  GitHub 复核  →  代码自检守卫
                                （OSV + issues + PR，含 closed）
```

⚠️ **第 2.5 步是第八~十一轮补进来的**（第十轮顺序反了，白写一套 PoC）：
**写 PoC 之前先查**一遍公开记录，挡掉"早已被报过"的。
⭐ 第十一轮实测：8 个候选一次过完，**5 个在选靶阶段即被排除**，其中两个若不前置就会白写 PoC
（`request-filtering-agent` 的 README 直接写着 "not a security boundary"；`superstruct` 的 #1301 是别人已提的）。
⭐ **四道闸（契约/层级/公开/落地）与各自的实测反例 → `whitebox-disclosure-gate`。**

**1. 必要条件定候选** —— 一句话能说清的「有该漏洞的必要条件」：
| 漏洞类 | 必要条件 |
|---|---|
| Zip Slip | **会往磁盘解压归档** |
| XXE | **会解析外部/不可信 XML** |
| 路径穿越 | **把（请求/调用方提供的）路径映射成文件系统路径** |

**2. OSV 反查**（`https://api.osv.dev/v1/query`，`ecosystem=Maven`）—— 排除有该类 CVE 的。
⚠️ **必须扫该 groupId 下的全部 artifact**：公告常挂在**兄弟包**上 ——
实测：查 `nanohttpd` **0 条**，CVE-2020-13697 却挂在 **`nanohttpd-nanolets`** 上。
**只查单包 = 系统性假阴性。**（列 artifact 用 Maven Central 的目录列表即可。）
⭐ **反着用才成立**：正着用 CVE 库 = 挑已修过的。

**3. GitHub 复核** —— issues / PRs 搜关键词（`traversal` / `zip slip` / `security`）。
**4. 代码自检守卫** —— 见 §一③ 的表。

⚠️ **「查到 0 条」要问一句「是不是我查窄了」** —— 第 2 步的假阴性就是这么发现的。

### 二·五、⚠️ 必要条件要在**对的 artifact** 里找（v095 实测四个候选）

第 1 步「必要条件」看着简单，实战里**四种形态**，判错会把"有戏"的排掉、或把"没戏"的留下：

| 形态 | 实测例子 | 怎么判 |
|---|---|---|
| ① **单文件自带** | **jlhttp**：整个服务器一个 `HTTPServer.java` | 直接读 ✅（本轮的命中就在这一档） |
| ② **跨两个 artifact** | **rapidoid**：映射在 `rapidoid-commons`（`IO`/`Res`），服务在 `rapidoid-http-fast`（`StaticResourcesHandler`） | **顺着调用链找** —— 只扫单包会得出"必要条件不成立"的**错误结论** |
| ③ **框架委托给下层** | **javalin**：23 个 artifact 里都没有"请求路径→文件系统"；`ResourceHandler` 只是 **SPI 接口**，实现落在 **Jetty** 侧 | **要审就审下层**（Jetty），别把上游框架当靶子 |
| ④ **压根不提供该功能** | **simple-http**：全组 5 个 artifact 无映射；`simple` 5.1.6 里 `File*` 类全是**上传/缓冲**（`FileUploadConsumer`/`FileBuffer`） | **排除**（用户自行实现的文件服务与本库无关） |

⭐⭐ **一句话判据：必要条件「本 artifact 内没找到」有三种可能 —— 在别的 artifact、在下层依赖、或本就没有。**
**先归因到哪一种，再决定"排除"还是"继续"。** 与第 2 步「OSV 必须扫整个 groupId」是同一族错误：
**查窄了会得到系统性假阴性，而它长得和"真的没有"一模一样。**

⭐ **两种"排除"要分开记**（本轮三个候选正好各占一种）：
- **有显式守卫** → 真排除（rapidoid：`HttpUtils.resName()` 里 `!path.contains("..")`，否则抛 `Invalid path!`）；
- **功能不在它身上** → 不是"安全"，是"**靶子选错了**"（javalin / simple-http）——
  ⚠️ 后者**不能**写成"已加固"，否则下一轮会以为查过了。

---

### 二·六、⭐ 判守卫：**`startsWith` 比较的是「字符串」还是「路径」**

⚠️ **「有没有守卫」不能只看关键词。** jlhttp **同时**做了 `getCanonicalFile()`（看着像"规范化过了"）
**和** `startsWith` 校验 —— 结果**两个都没拦住**：因为 `startsWith` 是**字符串**前缀比较，
base `…/www` 会放行兄弟目录 `…/www-secret`（CWE-22；**1.3~3.2 共 11 版未修**）。

⭐ **判守卫写法（Java / JS 对照表）、四种「0 CVE」形态、以及「我自己的验证脚本判据写错」
（`startsWith('..')` 假阳性 170→0）→ 全部见 `whitebox-guard-review`。**
**一句话**：守卫要按**路径元素**比，不按**字符串前缀**比。

## 三、选素材的两条硬判据

- **根因形态必须落在规则库覆盖面内**（先看规则库的 `kind` 清单）—— 否则必然 0 命中，产出全是噪声；
- **漏洞版与修复版的差异越小越好** —— 差异越小根因越干净，差异大的会被版本演进淹没。
  实测：zt-zip 1.12→1.13 **只 1 个文件变**（选它）；cron-utils 9.0.2→9.1.6 **60 个文件变**（弃）。

⭐ **不是每个 CVE 都值得做变体分析 —— 先看「修复的形态」**：

| 修复形态 | 值不值得 |
|---|---|
| ✅ **「加一个可复用的守卫」** | **有值**（Zip Slip / XXE 都是这一类） |
| ❌ 「往黑名单加一个类名」 | 无值（jackson-databind 式） |
| ❌ 「只改版本号」 | 无值 |

做法：拉 `patch_info`（**修复后的方法源码**）按关键词统计形态 —— **比读 diff 省事**。

## 四、候选出来之后：**查「它在哪个版本被修」**

⭐⭐ **不查这一步，就分不清 0day 与陈旧问题。**
做法**极便宜**：把该库相邻几个版本的 `sources.jar` 拉下来，看那一行还在不在。

实测三种结局，各自该怎么叫：

| 查到的 | 性质 | 能不能叫 0day |
|---|---|---|
| 已修（最新版有守卫） | **陈旧问题** | ❌ 不能 |
| 未修 + **无任何公开记录** | 可能是新发现 | ✅ 可以先当 0day 报 |
| 未修 + **有公开讨论/case/PR** | **已知未修的流程盲区** | ❌ **不能**（但仍有价值：SCA 零告警） |

⭐ **再补一个便宜的判据：查它是不是"一直如此"**（v094，jlhttp）——
把**全部历史版本**的 sources 拉下来比对那一行：11 个版本**逐字相同** ⇒
**不是回归，是长期存在**；这既提高"没人报过"的可信度（这么多版本都没人发现），
也说明**修法要一次性覆盖老版本**（下游可能锁在 1.x）。
⚠️ 反过来：如果只有旧版本有、新版修了 → 那是**陈旧问题**，别当新发现。

## 五、一页速查

| 步骤 | 动作 | 判据 / 坑 |
|---|---|---|
| 1 | 定**必要条件** | 一句话说清「有该漏洞的必要条件」 |
| 2 | **OSV 反查** | **扫该 groupId 全部 artifact**；正着用 = 挑已修过的 |
| **2.5** | ⭐ **前置公开记录检查** | **OSV + issues + PR（含 closed）**；只查 OSV 会误判成"新发现" |
| 3 | **GitHub 复核** | 有公开讨论但无 CVE = **已知未修**，**别叫 0day** |
| 4 | **代码自检守卫** | 一处都没有 → 值得深挖；集中在单一入口 → 排除 |
| 5 | 出候选 | **查它在哪个版本被修**；判「值可不可控」不是「有没有守卫」 |
| 6 | 确认 | ⭐ **PoC 是「候选 → 确认」的分水岭**，别停在「结构上存在」 |

⚠️ 最后一条是踩出来的：本机 **Java 21 可用**，拉 jar + 写 20 行 PoC 就能把
「读代码觉得有洞」变成「跑出来确实逃逸」。**PoC 的向量设计本身就是技术活** ——
`/../x` 与 `../x` 是**两种语义**（`new File(parent, "/x")` 在 Unix 上被当**绝对路径**），
只测一种 = 把「没测到」当成「没有」；且**必须用原始 socket**（HTTP 客户端会先规范化掉 `/../`）。
